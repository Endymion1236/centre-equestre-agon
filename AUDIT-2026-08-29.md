## 🔴 CRITIQUES

### S1 — Le navigateur décide si une place est réservée ou seulement tenue

**Fichier** : `src/app/api/enroll/route.ts`

`/api/enroll` est par ailleurs très bien écrit (transaction atomique, contrôle de capacité, filiation
enfant↔famille vérifiée depuis la fiche famille). Mais quatre champs du corps de requête sont
recopiés tels quels, sans vérification :

```ts
if (item.pending) {
  entry.pending = true;
  entry.holdUntil = item.holdUntil ?? dateExpirationHold(...);
}
if (item.paymentSource) entry.paymentSource = item.paymentSource;
if ("forfaitId" in item)  entry.forfaitId = item.forfaitId ?? null;
```

Le parcours `reserver` envoie loyalement `pending: true` : la place est tenue, puis levée par
`/api/cawl/status` à l'encaissement, et purgée par le cron sinon. Une famille authentifiée qui
appelle la route directement **en omettant** `pending` obtient une inscription définitive, que rien
ne purge et qu'aucun paiement n'accompagne. Elle peut aussi poser un `holdUntil` à cinq ans, ou se
déclarer couverte par un forfait inexistant via `paymentSource: "forfait"`.

Le parcours `inscription-annuelle` fait déjà cela nominalement (`src/app/espace-cavalier/inscription-annuelle/page.tsx:523`) :
il appelle `/api/enroll` avec `paymentSource: "forfait"` et **sans** `pending`. L'inscription à
l'année est donc ferme avant tout encaissement, pour tout le monde.

**Impact** : places de stage et de cours à l'année obtenues sans paiement, invisibles dans les
impayés puisque aucun `payment` n'est créé.

**Correctif** : imposer `pending: true` côté serveur pour toute inscription famille, calculer
`holdUntil` avec `dateExpirationHold()` (déjà présente), vérifier que le `forfaitId` annoncé existe,
appartient à la famille et est actif. N'autoriser une inscription ferme que si le jeton porte le
claim staff.

### S2 — Le contrôle serveur des prix tourne en mode silencieux

**Fichiers** : `src/lib/server-pricing.ts`, `src/app/api/cawl/checkout/route.ts:78`, `firestore.rules:68`

`server-pricing.ts` est un bon module : il recharge le tarif source des créneaux depuis Firestore,
borne chaque ligne entre son plancher et le tarif semaine, recalcule l'acompte et journalise tout
dans `pricing_audit`. Il est branché dans le checkout. Mais son verdict n'est appliqué que si une
variable est positionnée :

```ts
const ENFORCE = process.env.CAWL_PRICING_ENFORCE === "true";
if (willBlock) return NextResponse.json({ code: "PRICING_MISMATCH" }, { status: 400 });
```

Cette variable n'apparaît nulle part ailleurs dans le dépôt — ni dans `.env.local.example`, ni dans
`vercel.json`, ni dans la documentation. En son absence, le module observe sans jamais bloquer, et le
montant débité reste celui envoyé par le client :

```ts
if (totalTTC && totalTTC > 0) {
  totalCents = Math.round(totalTTC * 100);   // totalTTC vient du corps de requête
}
```

Le retour de paiement limite les dégâts : `/api/cawl/status` ne passe en `paid` que si le cumul
encaissé atteint le `totalTTC` du document `payments`. Sauf que les règles Firestore autorisent la
famille à **créer** ce document, avec le `totalTTC` de son choix :

```
allow create: if isStaff() || (isAuth()
  && request.resource.data.familyId == request.auth.uid
  && request.resource.data.status == "pending"
  && (request.resource.data.paidAmount == 0 || …));   // aucune borne sur totalTTC
```

Un stage à 175 € déclaré à 3 €, payé 3 €, ressort donc en `paid`, avec numéro de facture définitif,
confirmation des places et points de fidélité.

**Correctif** : relire la colonne `wouldBlock` de `pricing_audit` (prévue exactement pour ça), puis
poser `CAWL_PRICING_ENFORCE=true` dans Vercel. Étendre ensuite l'audit aux paiements sans `paymentId`
(inscription annuelle groupée), aujourd'hui hors périmètre. Ajouter la variable à `.env.local.example`.

### S3 — Une carte refusée génère un bon cadeau valide

**Fichier** : `src/app/api/bon-cadeau/status/route.ts:59`

`src/lib/cawl-status.ts` documente l'incident du 30 juillet 2026 : la route de retour considérait un
paiement comme réussi dès que le hosted checkout était en `PAYMENT_CREATED`, alors que ce statut
décrit la *session* et qu'un refus bancaire en crée une aussi. `deciderPaiement()` a été écrit pour
que « les deux chemins ne puissent pas diverger ». `/api/cawl/status` et `/api/cawl/webhook`
l'utilisent.

`/api/bon-cadeau/status` ne l'utilise pas, et contient la ligne d'origine, mot pour mot :

```ts
const isSuccess = httpStatus === 200 &&
  (["CAPTURED","PAID","PENDING_CAPTURE"].includes(paymentStatus)
   || hcStatus === "PAYMENT_CREATED");     // ← le bug de juillet
```

Derrière ce test, `traiterBonCadeauSession()` génère le bon, enregistre la recette et envoie l'email.
Le webhook, lui, est correct : il ne fera rien. Le bon existe donc, encaissable au club, sans
contrepartie bancaire.

**Correctif** : `deciderPaiement(paymentStatus) === "succes"`. Une ligne.

## 🟠 ÉLEVÉS

### S4 — Vérification RETURNMAC contournable (`/api/bon-cadeau/status:49`)

Le secret partagé avec CAWL n'est comparé que si les deux valeurs sont présentes :

```ts
if (sess.returnMac && returnMac && sess.returnMac !== returnMac) return cancel();
```

Appeler l'URL sans paramètre `RETURNMAC` saute entièrement le contrôle. À comparer avec
`/api/cawl/status`, qui refuse d'emblée si l'un des deux manque puis compare avec `timingSafeEqual`.
Combiné à S3, il suffit d'un `hostedCheckoutId` pour déclencher le traitement d'un bon.

**Correctif** : reprendre le schéma de `/api/cawl/status`.

### S5 — Les droits admin s'accordent sur un email non vérifié

**Fichiers** : `src/lib/api-auth.ts:38`, `firestore.rules:11`, `src/lib/auth-context.tsx:52`, `src/app/api/admin/reset-base/route.ts:28`

Trois adresses ouvrent l'administration complète, sans que `email_verified` soit jamais consulté :

```ts
export function isAdminToken(decoded: any): boolean {
  return decoded.admin === true || ADMIN_EMAILS.includes(decoded.email || "");
}
```

L'application expose `createUserWithEmailAndPassword` : l'inscription par email/mot de passe est
active. La seule chose qui empêche un inconnu de créer un compte portant l'une de ces adresses et
d'hériter des droits, c'est le réglage « une seule adresse par compte » de la console Firebase, plus
le fait que ces comptes existent déjà. Deux protections externes au code, qu'aucun test ne surveille.

**Correctif** : n'accorder l'admin que sur le claim `admin === true`. Si le repli par email doit
rester pour dépanner une base de test, le conditionner à `email_verified === true` **et** à un
environnement non-production. La liste est par ailleurs recopiée dans 4 fichiers.

### S6 — Aucun en-tête de sécurité HTTP

Ni `next.config.ts` (qui définit pourtant redirections, images, compression et Sentry) ni
`vercel.json` ne déclarent de fonction `headers()`. L'application est servie sans
`Content-Security-Policy`, `Strict-Transport-Security`, `X-Frame-Options`, `Referrer-Policy` ni
`Permissions-Policy` — pour une application qui manipule des fiches sanitaires de mineurs, des IBAN
SEPA et une caisse NF525.

**Correctif** : bloc `async headers()` dans `next.config.ts`. Commencer par HSTS,
`X-Content-Type-Options`, `X-Frame-Options: SAMEORIGIN` et `Referrer-Policy` (sans risque), puis CSP
en `Report-Only` avant de durcir. Attention au tunnel Sentry `/monitoring` et à Firebase.

### F1 — Un numéro de facture attribué depuis le navigateur, sans transaction

**Fichier** : `src/app/admin/paiements/TabImpayes.tsx:490`

`src/lib/invoice-number.ts` est écrit avec soin : transaction Firestore atomique, compteur par année,
trace systématique dans `invoice_audit`, en-tête citant l'art. 242 nonies A du CGI. Quatre chemins
l'utilisent correctement (`/api/invoice/next-number`, retour CAWL, cron MIT, `lib/encaissement.ts`).

Un cinquième ne l'utilise pas. Le bouton « → Facture définitive » fait le travail à la main :

```ts
const counterSnap = await getDoc(counterRef);
const currentNum  = counterSnap.data()?.[`year_${year}`] || 0;
const nextNum     = currentNum + 1;
await setDoc(counterRef, { [`year_${year}`]: nextNum }, { merge: true });
const invoiceNumber = `F-${year}-${String(nextNum).padStart(4, "0")}`;
```

Lecture puis écriture, sans transaction : deux onglets, ou deux personnes au bureau qui convertissent
en même temps, produisent **deux factures portant le même numéro**. Et aucune n'apparaît dans
`invoice_audit`, la piste tenue précisément pour prouver la séquence.

**Correctif** : appeler `authFetch("/api/invoice/next-number")` comme le fait `lib/encaissement.ts`.
Puis retirer le droit d'écriture du client sur `settings/invoiceCounter`.

### F2 — Le webhook CAWL n'attribue jamais de numéro de facture

**Fichier** : `src/app/api/cawl/webhook/route.ts:229`

L'en-tête de `invoice-number.ts` annonce que le module est appelé par « encaissement UI, retour
checkout CAWL, prélèvement MIT du cron, **webhook** ». Le webhook est le seul à ne pas l'appeler : il
passe le paiement en `paid`, crée l'encaissement, confirme les places, attribue les points — mais
laisse `invoiceNumber` vide.

Or le webhook est justement le chemin qui sert quand la famille ferme son navigateur avant la
redirection. Ces ventes réglées restent des proformas `PF-…` jusqu'à intervention manuelle — via le
bouton du constat précédent.

**Correctif** : appeler `attribuerNumeroFacture()` dans la branche de confirmation, avec
`attributedBy: "system:cawl-webhook"`, sous la même condition que la route de retour.

### F3 — Retour navigateur et webhook ne mesurent pas le même montant attendu

| | `/api/cawl/status` | `/api/cawl/webhook` |
|---|---|---|
| Montant attendu | `cawl_sessions.totalCents` (montant demandé) | `payments.totalTTC` |
| `paidAmount` | cumulé : `(pData.paidAmount\|\|0) + montantPayé` | écrasé : `totalTTC` |
| Statut final | `paid` si le cumul couvre le total, sinon `partial` | `paid` d'emblée |
| Numéro de facture | attribué | jamais (cf. F2) |

La route de retour commente explicitement son choix : le référentiel doit être le montant demandé,
« qui gère nativement les liens de paiement **partiels** (acompte 30 € sur une commande de 175 €) ».
Le webhook compare ces 30 € encaissés aux 175 € du document, conclut à une incohérence, marque
`amountMismatch` + `needsReview` et refuse la confirmation.

**Impact** : un lien de paiement partiel fonctionne si la famille revient sur le site, et se retrouve
bloqué en « à vérifier » si elle ferme son navigateur — un comportement qui dépend du geste du
client, donc difficile à reproduire quand on le signale.

**Correctif** : aligner le webhook sur la route de retour. Idéalement, extraire la confirmation dans
un module partagé — c'est ce qui a été fait avec succès pour `deciderPaiement()` après juillet.

## 🟡 MOYENS

### S8 — La sauvegarde quotidienne part par email, en clair, chaque nuit
`/api/cron/daily-backup` sérialise la base en JSON, l'écrit dans Storage puis l'envoie **en pièce
jointe** aux gérants. Export nominatif complet (familles, enfants, dates de naissance, coordonnées,
fiches sanitaires) déposé chaque jour dans une boîte Orange et une boîte Gmail. Une compromission de
boîte livre l'intégralité du fichier clients ; et cette copie échappe à toute politique de
conservation RGPD (le cron purge Storage à 30 jours, rien ne purge les boîtes). La copie Storage vit
en outre dans le **même** projet Firebase que les données : elle protège de l'erreur de manipulation,
pas de la perte du projet.
→ Lien signé à durée limitée plutôt que pièce jointe ; copie hors projet.

### F4 — Le fichier d'index Firestore n'est pas déployé et il est incomplet
`firebase.json` déclare les règles Firestore et Storage, mais **pas les index** :
```json
{ "firestore": { "rules": "firestore.rules" }, "storage": { "rules": "storage.rules" } }
```
`firestore.indexes.json` n'est donc jamais poussé : 6 index pour une vingtaine de requêtes
composites. Deux exigent formellement un index composite et ne l'ont pas :
- `galerie_photos` — `where("category","==") + orderBy("order")` (`src/hooks/useGaleriePhotos.ts:49`).
  En cas d'index manquant, le `onSnapshot` tombe en erreur et la galerie reste vide.
- `notes-seance` — `where("creneauId","==") + orderBy("createdAt","desc")` (`EnrollPanel.tsx:491`).
  Le code porte déjà le commentaire *« Index composite manquant → fallback sans orderBy »*.

→ Ajouter `"indexes": "firestore.indexes.json"` à `firebase.json`, resynchroniser via
`firebase firestore:indexes`, retirer les replis.

### F5 — Le prélèvement des soldes de stage est planifié deux fois par jour
`charge-stage-balances` est déclenché par le cron Vercel à 08:00 UTC **et** à 20:00 UTC par le
fan-out de `daily-emails`. L'idempotence tient (`soldeReminderSentAt`), mais ce marqueur n'est posé
qu'**après** le débit réussi, dans une écriture séparée : si le prélèvement CAWL aboutit et que
l'écriture Firestore échoue, la passe suivante re-débite.
→ Retirer l'une des deux planifications ; poser un verrou *avant* l'appel MIT (`cawl-lock.ts` fait
déjà cela pour le checkout).

## 🟢 CE QUI EST SOLIDE

- **Périmètre API refermé** — 137/144 routes authentifiées contre 44 % en avril. Les 7 restantes sont
  publiques par conception (planning, poneys, magic link, satisfaction par jeton, achat de bon).
- **Règles Firestore sérieuses** — 78 collections, refus par défaut en catch-all, et une **liste
  blanche** sur `settings` plutôt qu'une liste noire, qui a refermé la fuite du jeton OAuth Gmail.
- **Inaltérabilité comptable respectée** — `encaissements`, clôtures et fonds de caisse en écriture
  définitive, avec seulement 3 champs de rapprochement bancaire modifiables (NF525 / art. 286-I-3°bis).
- **Journaux infalsifiables** — `audit_log`, `invoice_audit`, `agent_actions`, `resetLogs` en écriture
  fermée *y compris pour l'admin*. « Un journal qu'on peut réécrire ne prouve rien » (commentaire des règles).
- **Retour de paiement durci** — RETURNMAC comparé en temps constant, verrou anti-doublon partagé
  entre webhook et retour, contrôle de montant, `deciderPaiement()` centralisé après l'incident du 30/07.
- **Inscription serveur atomique** — `/api/enroll` inscrit « partout ou nulle part », pour qu'un stage
  ne soit jamais à moitié réservé et facturé en entier.
- **Limitation de débit là où ça coûte** — IA, TTS, Whisper, borne, lecture de RIB, avec repli
  permissif en cas d'incident Firestore plutôt que blocage.
- **Connexion par lien magique bien pensée** — réponse générique quoi qu'il arrive, délai aléatoire
